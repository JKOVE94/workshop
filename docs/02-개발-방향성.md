# 개발 방향성 (Claude Code 인수인계용)

> **스코프 변경(2026-11-06)**: 앱은 1부 활동 전용으로 축소했고 2부는 범위 밖이다. 이 문서의 2부·캐릭터·프로필 내용은 보류이며, `03-1부-MVP-스코프.md`가 우선한다.

기획은 `docs/01-기획.md`. 이 문서는 "어떻게 만들 것인가"만 다룬다.
베이스는 마니또 앱(doc_manito_game) 포크이고, 현재 레포에는 옛 기능이 그대로 남아 있다.

## 0. 원칙

1. **스텝 엔진 우선**: 모든 화면은 관리자가 넘기는 `program_steps` 한 줄에 종속된다. 활동별 기능은 스텝 종류(kind) 하나로 꽂는다.
2. **미확정 규칙은 설정값(config jsonb)으로**: 기획 체크리스트가 안 닫혀도 개발은 진행한다. 점수·시간·인원 같은 값은 코드에 박지 않는다.
3. **당일 장애 대비**: 교회 와이파이는 믿지 않는다. 모든 점수 입력에 관리자 수동 입력 경로를 둔다. 종이 점수판이 최후 수단이다.
4. **부수효과는 멱등하게**: 스텝 진입 시 팀 편성·목자 배정은 이미 있으면 다시 섞지 않는다. 재셔플은 명시적 버튼으로만 한다.
5. **기존 마니또 인프라 재사용**: 인증, 실시간 갱신, 단일 순환 매칭, 테스트 봇은 그대로 쓴다.

## 2. 데이터 모델 (초안)

```
events            id, name, current_step_id, revision, created_at
participants      id, event_id, name, pin_hash, birth_date, part, fav_song, tmi jsonb(3), character jsonb
program_steps     id, event_id, part(1|2), sort, kind, title, config jsonb, status(pending|active|done)
rosters           event_id, part, participant_id, role(player|facilitator|observer)   -- 1부/2부 명단 분리
teams             id, event_id, part, name, color
team_members      team_id, participant_id
score_events      id, event_id, team_id, step_id, delta, reason, meta jsonb, created_at   -- append-only
amen_matches      id, step_id, team_a, team_b, player_a, player_b, status, meta jsonb
amen_traits       id, match_id, speaker_id, figure, trait, ok, created_at
hum_songs         id, event_id, title, team_id
word_cards        id, event_id, word, is_trap, qr_token   -- 내 양은 내 음성을 들으며
card_scans        id, card_id, scanner_id, team_id, ok, created_at
shepherd_links    id, event_id, shepherd_id, sheep_id, active, created_at, ended_at   -- 이력 보존
shepherd_notes    id, link_id, kind(cheer|note|prayer), body, created_at
missions          id, step_id, text   /   mission_done (participant_id, mission_id)
guesses           participant_id, guessed_shepherd_id
```

- 팀 점수 = `score_events` 합계. 수정은 삭제가 아니라 보정 행(음수 delta) 추가.
- 보안 모델은 마니또와 동일: RLS ON, 정책 없음, 모든 접근은 Route Handler + service_role. 클라이언트는 `events.revision` 변경만 구독한다.
- 생년월일은 연도 포함 저장하되 화면에는 월·일만 노출한다. 행사 후 파기용 관리자 버튼을 둔다.

## 3. 스텝 엔진

```ts
type StepKind =
  | 'entry' | 'roster_close' | 'hum_team' | 'amen' | 'one_voice'
  | 'sheep_voice' | 'part1_result' | 'part2_checkin' | 'shepherd_assign'
  | 'free_time' | 'final_guess' | 'reveal';

interface StepModule {
  kind: StepKind;
  Player: React.FC<{ state: PlayerState }>;   // 폰
  Stage:  React.FC<{ state: StageState }>;    // 빔
  Admin:  React.FC<{ step: Step }>;           // 관리자 패널
  onEnter?: (ctx) => Promise<void>;           // 멱등 부수효과 (팀 편성, 목자 배정)
}
```

- `src/lib/steps/registry.ts`에 kind → 모듈 매핑. 스텝 추가 = 파일 하나 + 등록 한 줄.
- 관리자 액션: 다음, 이전, 건너뛰기, 순서 변경, 스텝 추가·삭제. 전환은 `current_step_id` 갱신 + `revision` 증가 한 트랜잭션.
- 스텝 전환이 되돌려져도 데이터는 지우지 않는다. 진입 부수효과가 멱등이므로 이전/다음을 눌러도 안전해야 한다.
- 상태 응답은 역할별 뷰로 만든다 (`views.ts`): player / stage / admin. 목자 연결은 player 뷰에 본인 양만, admin 봉인 모드에서는 연결을 아예 내려주지 않는다.

| 경로 | 용도 |

## 5. 활동별 구현 메모

**캐릭터**: SVG 레이어(몸통, 색, 눈, 입, 귀, 소품)를 JSON으로 저장하고 `<Character mode="base|sheep|shepherd|hidden" />` 한 컴포넌트로 렌더. 참고 이미지가 오면 비율만 맞춘다. 외부 이미지 에셋은 쓰지 않는다.

**허밍 팀 찾기** (`hum_team`): 곡 수 = 팀 수. 진입 시 1부 명단을 곡별 균등 분배(멱등). 폰에는 내 곡만, 빔은 타이머 후 팀 공개.

**아멘 게임** (`amen`): 3팀이면 리그 3경기 대진 자동 생성, 출전자 선택 시 이미 출전한 사람은 비활성. 진행자 화면에서 인물·특성 태그 입력, 특성 중복이면 빔 경고. 5초 타이머는 서버 시각 기준(useLiveState의 clock offset). 승점 규칙(승·무·패 점수, 타이브레이크)은 `config`로.

**한마음과 한 입으로** (`one_voice`): 팀 인원 최솟값 N으로 글자 수 고정, 단어는 N글자만 필터. 라운드 r에서 시작자는 (r mod N). 폰에는 내 순서와 내 글자(공개 방식은 config), 판정은 관리자 버튼(성공/실패).

**내 양은 내 음성을 들으며** (`sheep_voice`): `word_cards`에서 인쇄 시트 생성 (카드당 QR = `/s/{token}`, 작게). 스캔 시 서버가 현재 스텝·팀·정오답을 판정해 `score_events`에 기록. 같은 카드 중복 스캔은 무시. 스캔 담당자(양/목자)는 config. 규칙이 미확정이므로 처음엔 "관리자 수동 +1/-1" + "QR 스캔 연동" 둘 다 열어 둔다.

**카드 시트 인쇄**: 관리자 페이지에서 A4 그리드 HTML을 열어 브라우저 인쇄. 서버사이드 PDF는 만들지 않는다. QR 생성은 `qrcode` 패키지 사용.

**비밀 목자** (`shepherd_assign`): 2부 명단 확정 후 `buildSingleCycle`로 고리 생성, 이미 `shepherd_links` 활성 행이 있으면 건드리지 않음. 최소 4명 미만이면 관리자에게 경고.
- 이탈 X: A→X→B 를 A→B 로. 기존 행 2개 `active=false`, 새 행 1개.
- 합류 J: 임의의 A→B 를 A→J→B 로. 행 1개 종료, 새 행 2개.
- 바뀐 목자에게만 "목자 교대" 알림 플래그.
- 이 연산은 순수 함수로 분리해 vitest로 검증한다 (고리 하나 유지, 자기 자신 연결 없음, 변경된 목자 수).
- 봉인 모드: 관리자가 참가자이기도 하므로 admin 뷰 API가 `shepherd_links` 자체를 반환하지 않는다. 문제 해결용 "공개" 버튼은 확인 모달 뒤에만.

**2부 TMI 공개**: 마니또의 키워드 해금 로직을 TMI 3개 단계 공개로 변경. 해금 조건(시간, 미션 완료)은 config.

## 6. 개발 순서

| Phase | 내용 | 완료 기준 |
| --- | --- | --- |
| 0 | 옛 기능 삭제, 빌드·테스트 통과, 환경변수·Supabase 프로젝트 연결 | `npm run build` 통과 |
| 1 | 스키마 + 스텝 엔진 + `/admin` 스텝 진행 + `/play`·`/stage` 껍데기 | 관리자가 스텝을 넘기면 폰과 빔이 따라 바뀜 |
| 2 | 입장, 캐릭터·프로필, 1부/2부 명단 분리 | 봇 포함 15명 입장 |
| 3 | 허밍 팀 찾기, 점수판(`score_events`), 수동 점수 입력 | 팀 편성·점수판 동작 |
| 4 | 비밀 목자 (배정, 이탈·합류, 봉인 모드, 쪽지·미션, 최종 추리, 공개) | 2부 전체 리허설 가능 |
| 5 | 아멘 게임, 한마음과 한 입으로 | 1부 중간 활동 가능 |
| 6 | 내 양은 내 음성을 들으며 + QR 카드 시트 | 메인 활동 가능 (규칙 확정 시) |
| 7 | 리허설: 봇 15명 전체 흐름, 모바일 실기기, 와이파이 끊김 테스트 | 체크리스트 통과 |

**2부(Phase 4)를 5·6보다 먼저 한다.** 2부는 기획이 확정됐고 마니또와 가장 가깝고, 1부 세부 규칙은 아직 열려 있다. 1부 활동은 규칙이 정해지는 대로 꽂는다. 일정이 모자라면 6 → 5 순으로 수동 진행(종이 + 관리자 점수 입력)으로 대체한다.

## 7. 테스트와 리허설

- 순수 로직(순환 배정, 이탈·합류, 팀 균등 분배, 리그 대진, 순서 회전)은 vitest 단위 테스트.
- 관리자 테스트 봇으로 15명 입장 → 전체 스텝 통과를 한 번에 돌리는 시나리오 스크립트를 `scripts/`에 둔다.
- 실기기: iOS Safari와 Android Chrome에서 QR 입장, 쿠키 유지, 화면 꺼짐 후 복귀 시 재동기화 확인.
- 빔 화면: 실제 해상도(1080p)와 멀리서 읽히는 글자 크기 확인.

## 8. 장애 대응 (당일)

- 점수 입력은 관리자 수동 경로가 항상 열려 있어야 한다.
- 폰 접속 실패자: 관리자 화면에서 대리 입장·대리 점수 가능.
- 5초 폴링이 있어 Realtime이 끊겨도 최대 5초 지연으로 따라온다. 오프라인 시 마지막 상태 유지 + "연결 끊김" 표시.
- 종이 점수판과 인쇄한 카드/단어 목록을 백업으로 준비.

## 9. 배포와 환경

- 배포: Vercel + Supabase (기존 마니또와 동일). 환경변수는 `.env.example` 참고, `.env.local`은 커밋 금지.
- 원격은 `origin = https://github.com/JKOVE94/workshop.git` 설정만 되어 있고 아직 push 전이다. 로컬에서 `git push -u origin main`.
- 행사 후: 생년월일·TMI 파기 버튼 실행, Supabase 프로젝트 정리.

## 10. 첫 작업 제안 (Claude Code에서)

1. `docs/01-기획.md`, `docs/02-개발-방향성.md`를 읽고 Phase 0부터 시작.
2. 옛 기능 삭제 목록(1절)을 기준으로 정리하고 `npm run build`, `npm test` 통과 확인 후 커밋.
3. Phase 1의 스키마 마이그레이션(2절)과 스텝 레지스트리(3절)를 설계해 먼저 보여 준 뒤 구현.
